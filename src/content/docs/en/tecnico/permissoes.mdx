## Overview

The system's access control defines **what each user can see and do**. It combines **screens** (URLs), **actions** (view, add, edit…) and **profiles** that group these permissions and are assigned to users. Everything is managed in the **Authenticator** module.

<Callout type="info" title="Where to configure">
Profiles, groups, screens and permissions live in the **Authenticator** module (Profile, Group, Module, URL and User screens).
</Callout>

  ]}

## How it fits together

1. **Screens** (URL) are organized by **Module**.
2. A **Profile** defines, per screen, what is **Allow/Deny** for each action.
3. The **User** receives one or more **Profiles** (and can belong to **Groups**).
4. An **Extra Permission** can grant a specific method outside the profile.

<Callout type="cuidado" title="Deny takes precedence">
When combining profiles and permissions, an explicit **"Deny"** tends to prevail over an "Allow". When building a profile, check the combined effect before granting access to sensitive screens.
</Callout>

## Relationship with other processes

- **Authenticator:** the Profile, Group, Module, URL and User screens manage all of this.
- **APIs:** [API](/en/tecnico/apis) calls also respect this permission model.
- Many flows cite **responsible groups** for approval (e.g., ADM, Credit, Tax) — those groups rely on the profiles/permissions described here.

<Callout type="info" title="How profile and screen connect">
Each of these profiles has, per screen, its **Allow/Deny** for each action. That combination (profile × screen × action) is edited in the Authenticator's **Profile** screen — it is what actually grants each person's access.
</Callout>
