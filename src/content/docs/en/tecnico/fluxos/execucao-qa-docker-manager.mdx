## Overview

This flow standardizes the creation of **isolated test environments** from specific Git **branches**, using the internal **QA Docker Manager** tool. The goal is to let QA analysts spin up, independently and **without advanced Docker or Git knowledge**, a complete environment to validate a feature before it is merged into the main branch.

The scope covers **creating, monitoring and accessing** the Docker containers generated from branches hosted on GitHub. It does not cover running the test cases themselves, nor the functional acceptance criteria — only **preparing the environment** where tests will run.

## When to use this flow

- Validate a feature on a specific branch before the merge.
- Test several branches at the same time, in isolated environments.
- Quickly provide an environment to a new QA member, without requiring prior Docker or Git experience.

**Audience:** QA analysts responsible for branch validation; developers who need to validate an isolated branch before merging; and new QA members without prior Docker or Git experience.

## Preconditions

- **Docker Desktop** must be installed, active and running before you start — a mandatory condition for every step that follows.
- The user must have **Git** installed on the machine.
- The user must have access to the QA Docker Manager repository and to the repository/branch to be tested on GitHub.
- There must be network/VPN connectivity to the required services, where applicable.
- Access to repositories and branches follows **strictly the access already granted** per the S.I.N Implante System permissions — the tool grants no additional access.
- Authentication uses **each contributor's own Git user**; there is no generic or shared user for cloning.

## Flow at a glance

The process is split into two major blocks:

- **Block A — Local environment setup:** install and bring up the QA Docker Manager tool (Steps 1 to 6).
- **Block B — Branch test environment:** use the tool to clone and start the branch container (Steps 7 to 11).

<Callout type="atencao" title="Mandatory precondition">
Docker Desktop must be active and open before Step 1. If it is not running, every Docker command in the following steps will fail.
</Callout>

## Step by step — Block A (prepare the tool)

### Step 1 — Clone the QA Docker Manager repository

Get the tool's source code.

1. Open the repository `https://github.com/pablosdlima/QaDockerManager`.
2. Click the **"Code"** button.
3. Click the copy icon to copy the **clone URL (HTTPS)**.

**Expected result:** repository URL copied, ready for the clone command.

### Step 2 — Open the Git Bash terminal

1. Go to the Desktop (or another easy-to-reach folder).
2. Right-click an empty area.
3. Select **"Open Git Bash Here"**.

**Expected result:** Git Bash terminal open in the selected folder.

### Step 3 — Clone the repository via command line

In the Git Bash terminal, run:

```bash
git clone https://github.com/pablosdlima/QaDockerManager.git
```

**Expected result:** a new **"QaDockerManager"** folder is created, with the project files.

### Step 4 — Bring the tool up via Docker Compose

1. Open the **"QaDockerManager"** folder in VS Code (or a similar editor).
2. Open the editor's integrated terminal.
3. Run:

```bash
docker compose up -d --build
```

4. Wait for the build to finish.

**Expected result:** a completion message with status **"DONE"** and the image **"Built"**, the network **"Created"** and the container **"Started"**.

<Callout type="atencao" title="If the build fails">
Build time varies with the machine, network and the volume of dependencies — there is no fixed time. If the build fails, the terminal shows the error message and the process does not complete (no "DONE" or "Started") — in that case, the environment did not come up.
</Callout>

### Step 5 — Check the container in Docker Desktop

1. Open Docker Desktop.
2. Go to the **"Containers"** menu.
3. Find the matching container (e.g., **"qa-docker-manager"**) with a running status (green indicator).

**Expected result:** the container is listed as active, with the mapped port in the **"Port(s)"** column (e.g., **5058:8080**).

### Step 6 — Open the tool in the browser

In Docker Desktop, click the port shown for the container (e.g., **5058:8080**).

**Expected result:** the browser opens `localhost:5058`, showing the QA Docker Manager home screen.

## Step by step — Block B (create the branch environment)

### Step 7 — Fill in the new container data

On the **"New Container"** screen, provide:

1. **"Repository URL"** — the URL of the repository to test, **without the ".git" extension** (e.g., `https://github.com/company/project`, not `.../project.git`).
2. **"Branch"** — the branch name to test (e.g., `feature/QA-123-fix-login`).
3. **"Container Name"** — enter or accept the suggested name; it is used to tell environments apart among the running containers.

**Expected result:** the form filled with URL (no ".git"), branch and container name, ready to submit.

<Callout type="cuidado" title="URL without &quot;.git&quot;">
The URL must be provided **without the ".git" suffix**. Including that extension may cause the tool to fail to identify/clone the repository.
</Callout>

### Step 8 — Select the branch to test

Identify, in the source repository, the specific branch to validate.

1. Open the source repository (in the manual, the example is `https://github.com/pablosdlima/TesteDockerQA`).
2. Copy the **repository URL** and the **branch name** to use in the Step 7 form.

**Expected result:** URL and branch identified and ready to use.

### Step 9 — Bring up the branch container

1. Click **"START CONTAINER"**.
2. Wait for the repository clone.
3. Wait for the branch container(s) to finish starting.

**Expected result:** the container appears in the **"Existing Containers"** list, with the given name, status **"running"** (e.g., **3/3 running**), the associated branch and each service's ports (e.g., 5200, 5100, 5050).

### Step 10 — Access the branch test environment

Open the tested application, published on one of the ports generated for the container.

- In the **"Existing Containers"** list, click the port of the service to access (e.g., **:5200**), in the browser; **or**
- In **Docker Desktop**, find the container/service and open it via the mapped port in the **"Port(s)"** column.

**Expected result:** the branch application opens, in the browser (via QA Docker Manager) or directly in Docker Desktop.

### Step 11 — Validate the tested application

1. Check that the application home page loads correctly.
2. Browse the features according to the test script for the feature under review.

**Expected result:** the application loads successfully, ready for the functional tests planned by the analyst.

## Validations

Before starting the functional tests, confirm:

- The **QA Docker Manager** tool container is active in Docker Desktop.
- The container created for the branch is **"running"** across all expected services (e.g., 3/3 running).
- The associated branch matches exactly the one given in the form (Step 7).
- The application is reachable on the indicated port, with no loading errors.

<Callout type="info" title="Expected startup time">
Startup time depends directly on cloning the repository and averages around **3 to 5 minutes**. Longer times are usually related to the repository size or network quality.
</Callout>

## Closing the test environment

After the tests, close the environment to free resources. The **"Existing Containers"** screen offers the **"STOP"** and **"REMOVE"** buttons:

- **"STOP"** — halts the container's services, keeping it available for a new start.
- **"REMOVE"** — permanently deletes the container, also clearing the Docker image generated locally for that environment.

<Callout type="cuidado" title="Care when removing">
Because **"REMOVE"** clears the locally generated Docker image (not just the container), use it only after confirming the branch tests are finished — a new startup of the same branch will require a full image rebuild.
</Callout>

## Branch naming standard

Since the branch name is typed directly into the QA Docker Manager, a naming standard reduces typos and avoids failures from URL-incompatible characters (e.g., "#"). Official standard:

```text
<type>/<work-item-number>-<short-kebab-case-description>
Example: bugfix/4313-fix-loading-list-button
```

- **Type:** fixed lowercase vocabulary — `feature`, `bugfix`, `hotfix`, `refactor`, `chore` or `docs`.
- **Work item number:** only the Azure DevOps work item number, without prefixes ("TASK-") or symbols ("#").
- **Description:** short (3 to 6 words), in kebab-case, lowercase and without accents.
- **Author name:** not included in the branch — authorship is already tracked by Git/Azure DevOps.
