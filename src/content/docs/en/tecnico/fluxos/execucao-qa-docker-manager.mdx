## Overview

The **QA Docker Manager** is the web tool (Blazor Server) the QA team uses to **spin up and manage containerized test environments** from Git repositories. This flow describes how to **put the tool itself online** using Docker, from the terminal to accessing the interface in the browser.

The image is built in **multi-stage** form, which keeps the final image lean: the build stages use the .NET SDK, but the image that runs in production carries only what is needed to execute (the ASP.NET runtime, "git" and the "docker" client). Execution is orchestrated by a single **docker compose** command.

## When to use this flow

- Put the QA Docker Manager online for the first time on a server.
- Update the tool after a code change (rebuild the image).
- Restart, stop or inspect the tool's container.
- Confirm that the environment became reachable through the web interface.

## How to access

The flow runs in the **terminal**, in the project folder that holds the container files:

- `Dockerfile` — the multi-stage build recipe for the image.
- `docker-compose.yml` — orchestration (port, Docker socket, volumes, limits).
- `.dockerignore` — prevents sending `bin/`, `obj/`, `temp/` and `data/` to the build.

Once up, the interface is available at **`http://localhost:5058`** (or via the server IP).

## The build stages (multi-stage)

The `Dockerfile` is split into chained stages. Each stage reuses the result of the previous one, and only the **final** stage becomes the image that runs.

<DocTable
  headers={['Stage', 'What it does']}
  rows={[
    ['1. base', 'Starts from the ASP.NET runtime and installs the runtime tools: "git" (to clone repositories) and the "docker" client + "compose" (to command the host Docker).'],
    ['2. restore', 'Uses the .NET SDK and restores dependencies from the project file. This layer is reused from cache while dependencies do not change.'],
    ['3. build', 'Compiles the project in Release mode, reusing the restore already done.'],
    ['4. publish', 'Generates the published files, ready for production.'],
    ['5. final', 'Starts from the "base" stage and receives only the published files. This is the lean image that actually runs.'],
  ]}
/>

<Callout type="info" title="Why multi-stage">
The .NET SDK (needed to compile) is large. By separating compilation from execution, the final image does not carry the SDK — only the runtime and the published files. The result is a smaller image, faster to distribute and with a smaller attack surface.
</Callout>

## Step by step

### 1. Open the terminal in the project folder

Navigate to the folder that holds the `docker-compose.yml`:

```bash
cd path/to/QaDockerManager
```

### 2. Bring the application up

Build the image (if it does not exist yet) and start the container in the background:

```bash
docker compose up -d --build
```

- The **"--build"** option forces the image to be built from the `Dockerfile`.
- The **"-d"** option starts it in the background, freeing the terminal.
- On the **first run**, Docker pulls the base images (.NET SDK, runtime and Docker client); this can take a few minutes. Afterwards it is nearly instant thanks to caching.

### 3. Check that it is up

```bash
docker compose ps
```

The **"qa-docker-manager"** service should show as **"running"** and, after a few seconds, **"healthy"**.

<Callout type="dica" title="If it does not come up">
Check the application logs to understand why:

```bash
docker compose logs -f qa-docker-manager
```
</Callout>

### 4. Access the interface

Open the browser at **`http://localhost:5058`**. To access from another machine, replace `localhost` with the **server IP or name**: `http://YOUR-SERVER:5058`.

That's it — the tool is online and QA can register repositories and spin up environments from the screen.

## Rules and cautions

- The tool commands the **host Docker** through the socket `/var/run/docker.sock` (the "Docker outside of Docker" pattern). Without that mapping in the `docker-compose.yml`, it starts but **cannot** create environments.
- The **"temp"** (cloned repositories) and **"data"** (environment registry) folders are persisted by volume; they must not be deleted while the tool is in use.
- The `.dockerignore` is mandatory: without it, the build sends `bin/`, `obj/`, `temp/` and `data/` into the image, slowing the build and contaminating the image with runtime data.
- The **"docker compose down"** command removes only the tool's container; the test environments it created keep existing in the host Docker.
- To change the access port, edit only the left side of the mapping in the `docker-compose.yml` (e.g., **"8090:8080"** to access at `http://localhost:8090`).
