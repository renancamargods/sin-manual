## Overview

This is a **reference** page: what defines an order's "type" in S.I.N and what each SAP order code means (**ORB**, **ZKBB**, **ZKEB**, **KEB**...). For the step-by-step of **how** an operator builds an order and picks its items, see the flow **[Order Process - Items and Item Types](/en/tecnico/fluxos/processo-do-pedido-itens)**.

In S.I.N there is **no single "order type" field**. What classifies an order is the **Smart Operation** (`Pedidos_OperacaoInteligente`), which binds **two levels** of information:

<DocTable
  headers={['Level', 'Field', 'Purpose']}
  rows={[
    ['1. Business category', 'TipoOperacao', 'The nature of the operation: Sale, Bonus, Campaign, Consignment, Exchange, OPL Warehousing Shipment or Return. This is what the operator "sees" and what drives the pricing, payment and review rules.'],
    ['2. ERP order code', 'OrdemErp', 'The matching order type in SAP (ORB, ZKBB, ZKEB, KEB...). This code decides how the order enters the ERP and is invoiced.'],
  ]}
/>

In other words: **ORB, ZKBB, ZKEB and the like are SAP order codes** (the `OrdemErp` field), and each is tied to a business category. A single code can serve more than one category — for example, **`ORB`** is used for both **Sale** and **Campaign**.

<Callout type="dica" title="How to read a code">
The most common question ("what order is this ORB / ZKBB?") is answered by <strong>reading the table row</strong>: the code is the SAP order type; the <strong>category</strong> next to it is the business nature; the <strong>description</strong> (the <code>Observacao</code> field in the database) is the friendly name.
</Callout>

## Code convention

The codes follow a pattern that helps memorize them:

<DocTable
  headers={['Pattern', 'Meaning', 'Examples']}
  rows={[
    ['Z prefix', 'SIN custom order (the "Z" is SAP\'s customization range).', 'ZKBB, ZKEB, ZOR1, ZR00'],
    ['Y prefix', 'Export, bonus, exchange and return families.', 'YEXP, YEXB, YTRO, YROB'],
    ['No Z (ORB, KBB, KEB)', 'Variation of the same operation used in plants other than 1000.', 'ORB, KBB, KEB'],
    ['ORB', 'The "standard" sale — the ordinary sales order.', 'ORB'],
  ]}
/>

<Callout type="cuidado" title="ZKBB ↔ KBB and ZKEB ↔ KEB are not different operations">
They are the <strong>same operation</strong>, with the code swapped by <strong>plant</strong>. The system converts <code>ZKBB → KBB</code> (and <code>ZKEB → KEB</code>) automatically when the order's plant <strong>is not 1000</strong>. When you see "KBB" on an order, read it as "the ZKBB consignment shipment, just in another plant".
</Callout>

## The business categories

### Sale
The standard operation: the customer buys and the item is invoiced. It ranges from the ordinary sale (**`ORB`**) to special cases such as **export** (`YEXP`), **nationalized sale** (`YEXN`), **Lounge sale** (`ZOR1`) and **invoicing what was on consignment** (`ZKEB` / `KEB`).

### Bonus
Item sent to the customer **free of charge** (gift, donation, courtesy). It has its own review rules and limits. Includes the export (`YEXB`, `YBEX`) and nationalized (`YEBN`) variations.

### Campaign
Sale tied to a **campaign policy** (promotional price/condition). It reuses the sales codes (`ORB`, `ZOR1`), but the category changes because price and rules come from the campaign.

### Consignment (shipment)
Goods sent to the customer that **only become a sale once consumed**. It is the **shipment** that places the product at the customer (**`ZKBB`** / `KBB`). It does not invoice on its own — it is part of a cycle (see the callout below).

### Exchange
Replacement of an already-delivered item with another. It uses the **`Y`** family depending on what is being exchanged: sale (`YTRO`), bonus (`YBON` / `YDOA`) or OPL (`YOPL`). It is part of the **[Exchange, Return and Cancellation (TDC)](/en/tecnico/fluxos/troca-devolucao-cancelamento-tdc)** flow.

### OPL Warehousing Shipment
Shipment of material for **warehousing at a logistics operator** (`OPL1`) — not a sale to the end customer, but a movement to the logistics partner.

### Return
Return of goods to stock, generating **credit** or an adjustment. Each type of outbound has its mirrored return: sale return (`ZR00` / `DEVOLUCAO`), consignment return (`ZROB` / `YROB`), bonus return (`YRDB`), export return (`YDEX` / `YDBE`) and third-party return (`ZDIS`).

<Callout type="info" title="The consignment cycle (why there are so many similar codes)">
Consignment is a <strong>cycle</strong>, not a single order:
<br/>1. <strong>Shipment</strong> (<code>ZKBB</code>/<code>KBB</code>) — sends the product to sit at the customer.
<br/>2. <strong>Sale of what was consumed</strong> (<code>ZKEB</code>/<code>KEB</code>) — invoices what the customer used.
<br/>3. <strong>Return</strong> (<code>ZROB</code>/<code>YROB</code>) — collects what was left over.
<br/>That is why all three appear as distinct operations, each in its own category.
</Callout>

<Callout type="info" title="Where this data comes from">
The source is the <code>Pedidos_OperacaoInteligente</code> table (the <code>OperacaoInteligente</code> entity): <code>OrdemErp</code> = SAP code, <code>TipoOperacao</code> = category, <code>Observacao</code> = friendly description. The <code>ZKBB → KBB</code> swap by plant is done when building the order header for the integrator (<code>PedidoCapa</code>). Since this is registered content, the list may change — in case of divergence, the database is the source of truth.
</Callout>
