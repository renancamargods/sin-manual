## Visão geral

Este fluxo padroniza a criação de **ambientes de teste isolados**, a partir de **branches** específicas de um repositório Git, usando a ferramenta interna **QA Docker Manager**. O objetivo é permitir que analistas de QA subam, de forma independente e **sem conhecimento avançado de Docker ou Git**, um ambiente completo para validar uma funcionalidade antes da sua integração à branch principal.

O escopo cobre a **criação, o acompanhamento e o acesso** aos containers Docker gerados a partir de branches hospedadas no GitHub. Não fazem parte deste fluxo a execução dos casos de teste em si, nem os critérios de aprovação funcional — apenas a **preparação do ambiente** onde os testes serão executados.

## Quando usar este fluxo

- Validar uma funcionalidade em uma branch específica antes do merge.
- Testar várias branches ao mesmo tempo, em ambientes isolados.
- Disponibilizar rapidamente um ambiente para um novo integrante de QA, sem exigir experiência prévia em Docker ou Git.

**Público-alvo:** analistas de QA responsáveis pela validação em branches; desenvolvedores que precisem validar uma branch isolada antes do merge; e novos integrantes do time de QA sem experiência prévia em Docker ou Git.

## Pré-condições

- O **Docker Desktop** deve estar instalado, ativo e em execução antes de iniciar — condição obrigatória para todas as etapas seguintes.
- O usuário deve ter **Git** instalado na máquina.
- O usuário deve ter acesso ao repositório do QA Docker Manager e ao(s) repositório(s)/branch(es) a testar no GitHub.
- Deve haver conectividade de rede/VPN com os serviços necessários, quando aplicável.
- O acesso aos repositórios e branches segue **estritamente os acessos já liberados** conforme as permissões do S.I.N Implante System — a ferramenta não concede nenhum acesso adicional.
- A autenticação é feita com o **próprio usuário do Git** de cada colaborador; não há usuário genérico ou compartilhado para clonagem.

## Visão geral do fluxo

O processo se divide em dois grandes blocos:

- **Bloco A — Preparação do ambiente local:** instalar e subir a ferramenta QA Docker Manager (Etapas 1 a 6).
- **Bloco B — Criação do ambiente de testes da branch:** usar a ferramenta para clonar e subir o container da branch (Etapas 7 a 11).

<Callout type="atencao" title="Pré-condição obrigatória">
O Docker Desktop precisa estar ativo e aberto antes da Etapa 1. Se não estiver em execução, todos os comandos Docker das etapas seguintes falharão.
</Callout>

## Passo a passo — Bloco A (preparar a ferramenta)

### Etapa 1 — Clonar o repositório do QA Docker Manager

Obter o código-fonte da ferramenta.

1. Acessar o repositório `https://github.com/pablosdlima/QaDockerManager`.
2. Clicar no botão **"Code"**.
3. Clicar no ícone de copiar para copiar a **URL de clonagem (HTTPS)**.

**Resultado esperado:** URL do repositório copiada, pronta para o comando de clonagem.

### Etapa 2 — Abrir o terminal Git Bash

1. Acessar a Área de Trabalho (ou outro diretório de fácil acesso).
2. Clicar com o botão direito em uma área vazia.
3. Selecionar **"Open Git Bash Here"**.

**Resultado esperado:** terminal Git Bash aberto no diretório selecionado.

### Etapa 3 — Clonar o repositório via linha de comando

No terminal Git Bash, executar:

```bash
git clone https://github.com/pablosdlima/QaDockerManager.git
```

**Resultado esperado:** uma nova pasta **"QaDockerManager"** é criada no diretório, com os arquivos do projeto.

### Etapa 4 — Subir a ferramenta via Docker Compose

1. Abrir a pasta **"QaDockerManager"** no VS Code (ou editor similar).
2. Abrir o terminal integrado do editor.
3. Executar:

```bash
docker compose up -d --build
```

4. Aguardar a finalização do build.

**Resultado esperado:** mensagem de conclusão com status **"DONE"** e indicação de que a imagem foi **"Built"**, a rede **"Created"** e o container **"Started"**.

<Callout type="atencao" title="Se o build falhar">
O tempo de build varia conforme a máquina, a conexão de rede e o volume de dependências — não há um tempo fixo. Se o build falhar, o terminal exibe a mensagem de erro e o processo não conclui (não aparece "DONE" nem "Started") — nesse caso, o ambiente não subiu.
</Callout>

### Etapa 5 — Verificar o container no Docker Desktop

1. Abrir o Docker Desktop.
2. Acessar o menu **"Containers"**.
3. Localizar o container correspondente (ex.: **"qa-docker-manager"**) com status em execução (indicador verde).

**Resultado esperado:** container listado como ativo, com a porta mapeada na coluna **"Port(s)"** (ex.: **5058:8080**).

### Etapa 6 — Abrir a ferramenta no navegador

No Docker Desktop, clicar sobre a porta exibida para o container (ex.: **5058:8080**).

**Resultado esperado:** o navegador abre `localhost:5058`, exibindo a tela inicial do QA Docker Manager.

## Passo a passo — Bloco B (criar o ambiente da branch)

### Etapa 7 — Preencher os dados do novo container

Na tela **"Novo Container"**, informar:

1. **"URL do Repositório"** — a URL do repositório a ser testado, **sem a extensão ".git"** ao final (ex.: `https://github.com/empresa/projeto`, e não `.../projeto.git`).
2. **"Branch"** — o nome da branch a testar (ex.: `feature/QA-123-fix-login`).
3. **"Nome do Container"** — informar ou aceitar o nome sugerido; é usado para diferenciar o ambiente entre os containers em execução.

**Resultado esperado:** formulário preenchido com URL (sem ".git"), branch e nome do container, pronto para envio.

<Callout type="cuidado" title="URL sem &quot;.git&quot;">
A URL deve ser informada **sem o sufixo ".git"**. Incluir essa extensão pode causar falha na identificação/clonagem do repositório pela ferramenta.
</Callout>

### Etapa 8 — Selecionar a branch a ser testada

Identificar, no repositório de origem, a branch específica que será validada.

1. Acessar o repositório de origem (no manual, o exemplo é `https://github.com/pablosdlima/TesteDockerQA`).
2. Copiar a **URL do repositório** e o **nome da branch** desejada para usar no formulário da Etapa 7.

**Resultado esperado:** URL e branch identificadas e prontas para uso.

### Etapa 9 — Subir o container da branch

1. Clicar em **"SUBIR CONTAINER"**.
2. Aguardar a clonagem do repositório informado.
3. Aguardar a finalização da subida do(s) container(es) da branch.

**Resultado esperado:** o container aparece na lista **"Containers Existentes"**, com o nome informado, status **"rodando"** (ex.: **3/3 rodando**), a branch associada e as portas de cada serviço (ex.: 5200, 5100, 5050).

### Etapa 10 — Acessar o ambiente de teste da branch

Abrir a aplicação testada, publicada em uma das portas geradas para o container.

- Na lista **"Containers Existentes"**, clicar na porta do serviço a acessar (ex.: **:5200**), pelo navegador; **ou**
- No **Docker Desktop**, localizar o container/serviço e acessá-lo pela porta mapeada na coluna **"Port(s)"**.

**Resultado esperado:** a aplicação da branch testada é aberta, pelo navegador (via QA Docker Manager) ou diretamente pelo Docker Desktop.

### Etapa 11 — Validar a aplicação testada

1. Verificar se a página inicial da aplicação carrega corretamente.
2. Navegar pelas funcionalidades conforme o roteiro de testes da funcionalidade em análise.

**Resultado esperado:** aplicação carregada com sucesso, disponível para os testes funcionais planejados pelo analista.

## Validações

Antes de iniciar os testes funcionais, confirme:

- O container da ferramenta **QA Docker Manager** está ativo no Docker Desktop.
- O container criado para a branch está **"rodando"** em todos os serviços esperados (ex.: 3/3 rodando).
- A branch associada corresponde exatamente à informada no formulário (Etapa 7).
- A aplicação é acessível pela porta indicada, sem erros de carregamento.

<Callout type="info" title="Tempo esperado de subida">
O tempo de subida depende diretamente da clonagem do repositório e gira, em média, em torno de **3 a 5 minutos**. Variações acima disso costumam estar associadas ao tamanho do repositório ou à qualidade da conexão de rede.
</Callout>

## Encerramento do ambiente de teste

Após concluir os testes, encerre o ambiente para liberar recursos. A tela **"Containers Existentes"** oferece os botões **"PARAR"** e **"REMOVER"**:

- **"PARAR"** — interrompe a execução dos serviços do container, mantendo-o disponível para nova inicialização.
- **"REMOVER"** — exclui definitivamente o container, limpando também a imagem Docker gerada localmente para aquele ambiente.

<Callout type="cuidado" title="Cuidado ao remover">
Como o **"REMOVER"** limpa a imagem Docker gerada localmente (não só o container), use-o apenas após confirmar que os testes na branch foram concluídos — uma nova subida da mesma branch exigirá reconstrução completa da imagem.
</Callout>

## Padrão de nomenclatura de branches

Como o nome da branch é digitado diretamente no QA Docker Manager, padronizar a nomenclatura reduz o risco de erro de digitação e evita falhas por caracteres não compatíveis com URL (ex.: "#"). Padrão oficial:

```text
<tipo>/<numero-da-demanda>-<descricao-curta-em-kebab-case>
Exemplo: bugfix/4313-ajuste-botao-fila-romaneio
```

- **Tipo:** vocabulário fixo, em minúsculas — `feature`, `bugfix`, `hotfix`, `refactor`, `chore` ou `docs`.
- **Número da demanda:** apenas o número do work item do Azure DevOps, sem prefixos ("TASK-") ou símbolos ("#").
- **Descrição:** curta (3 a 6 palavras), em kebab-case, minúsculas e sem acentuação.
- **Nome do autor:** não incluído na branch — a autoria já é rastreada pelo Git/Azure DevOps.
