## Visão geral

O **QA Docker Manager** é a ferramenta web (Blazor Server) que a equipe de QA usa para **subir e gerenciar ambientes de teste em containers** a partir de repositórios Git. Este fluxo descreve como **colocar a própria ferramenta no ar** usando Docker, desde o terminal até o acesso à interface no navegador.

A imagem é construída em **multi-stage** (vários estágios), o que mantém a imagem final enxuta: os estágios de compilação usam o SDK do .NET, mas a imagem que roda em produção leva apenas o necessário para executar (runtime do ASP.NET, "git" e o cliente "docker"). A execução é orquestrada por um único comando de **docker compose**.

## Quando usar este fluxo

- Colocar o QA Docker Manager no ar pela primeira vez em um servidor.
- Atualizar a ferramenta após uma mudança no código (reconstruir a imagem).
- Reiniciar, parar ou inspecionar o container da ferramenta.
- Validar que o ambiente ficou acessível pela interface web.

## Como acessar

O fluxo é executado no **terminal**, na pasta do projeto onde ficam os arquivos de container:

- `Dockerfile` — receita de build multi-stage da imagem.
- `docker-compose.yml` — orquestração (porta, socket do Docker, volumes, limites).
- `.dockerignore` — evita enviar `bin/`, `obj/`, `temp/` e `data/` para o build.

Após subir, a interface fica disponível em **`http://localhost:5058`** (ou pelo IP do servidor).

## As etapas do build (multi-stage)

O `Dockerfile` é dividido em estágios encadeados. Cada estágio aproveita o resultado do anterior, e só o estágio **final** vira a imagem que roda.

<DocTable
  headers={['Estágio', 'O que faz']}
  rows={[
    ['1. base', 'Parte do runtime do ASP.NET e instala as ferramentas de execução: "git" (para clonar repositórios) e o cliente "docker" + "compose" (para comandar o Docker do host).'],
    ['2. restore', 'Usa o SDK do .NET e restaura as dependências a partir do arquivo de projeto. Camada reaproveitada por cache enquanto as dependências não mudam.'],
    ['3. build', 'Compila o projeto em modo Release, reaproveitando o restore já feito.'],
    ['4. publish', 'Gera os arquivos publicados, prontos para produção.'],
    ['5. final', 'Parte do estágio "base" e recebe apenas os arquivos publicados. É a imagem enxuta que efetivamente executa.'],
  ]}
/>

<Callout type="info" title="Por que multi-stage">
O SDK do .NET (necessário para compilar) é grande. Ao separar a compilação da execução, a imagem final não carrega o SDK — só o runtime e os arquivos publicados. O resultado é uma imagem menor, mais rápida de distribuir e com menor superfície de ataque.
</Callout>

## Passo a passo do processo

### 1. Abrir o terminal na pasta do projeto

Navegue até a pasta onde está o `docker-compose.yml`:

```bash
cd caminho/para/QaDockerManager
```

### 2. Subir a aplicação

Construa a imagem (se ainda não existir) e suba o container em segundo plano:

```bash
docker compose up -d --build
```

- A opção **"--build"** força a construção da imagem a partir do `Dockerfile`.
- A opção **"-d"** sobe em segundo plano, liberando o terminal.
- Na **primeira execução**, o Docker baixa as imagens base (SDK do .NET, runtime e cliente Docker); pode levar alguns minutos. Nas próximas vezes é quase instantâneo por causa do cache.

### 3. Verificar se subiu

```bash
docker compose ps
```

O serviço **"qa-docker-manager"** deve aparecer como **"running"** e, após alguns segundos, **"healthy"**.

<Callout type="dica" title="Se não subir">
Consulte os registros da aplicação para entender o motivo:

```bash
docker compose logs -f qa-docker-manager
```
</Callout>

### 4. Acessar a interface

Abra o navegador em **`http://localhost:5058`**. Para acessar de outra máquina, troque `localhost` pelo **IP ou nome do servidor**: `http://SEU-SERVIDOR:5058`.

Pronto — a ferramenta está no ar e o QA já pode cadastrar repositórios e subir ambientes pela tela.

## Regras e cuidados

- A ferramenta comanda o **Docker do host** pelo socket `/var/run/docker.sock` (padrão "Docker fora do Docker"). Sem esse mapeamento no `docker-compose.yml`, ela sobe mas **não consegue** criar ambientes.
- As pastas **"temp"** (repositórios clonados) e **"data"** (registro de ambientes) são persistidas por volume; não devem ser apagadas com a ferramenta em uso.
- O `.dockerignore` é obrigatório: sem ele, o build envia `bin/`, `obj/`, `temp/` e `data/` para dentro da imagem, deixando o build lento e a imagem contaminada com dados de execução.
- O comando **"docker compose down"** remove apenas o container da ferramenta; os ambientes de teste que ela criou continuam existindo no Docker do host.
- Para mudar a porta de acesso, altere só o lado esquerdo do mapeamento no `docker-compose.yml` (ex.: **"8090:8080"** para acessar em `http://localhost:8090`).

<Callout type="dica" title="Como ler o fluxograma">
Um único comando (<strong>docker compose up -d --build</strong>) dispara o build <strong>multi-stage</strong> e sobe o container. Na primeira vez, o Docker baixa as imagens base; nas próximas, aproveita o cache. Quando o status fica <strong>healthy</strong>, a interface está pronta em <strong>http://localhost:5058</strong>.
</Callout>
